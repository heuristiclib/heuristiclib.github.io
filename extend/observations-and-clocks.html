Observations and clocks ​

The analysis tools cover traces, best-so-far analysis, counters and durations. This page writes an analyzer that combines observation types and a clock of your own. To make an operation of your own observable, see Make the operation observable.

An analyzer over several observation types ​

An analyzer that combines different observation types derives from Analyzer<TResult> and implements IObservationReceiver<TObservation> once for each type. It needs three parts:

  • CreateSubstitutions places one observation wrapper per boundary with source.RecordingInto(this).
  • CreateExecutionNode creates an empty result for each run. The result implements IRunResult and synchronizes its own updates.
  • Each CreateRecorder looks up the run's result with results.Result(this) and returns the callback for its observation type.

This analyzer counts the candidates the mutator produces in each yielded iteration. Mutation observations add to a pending count, and each iteration observation closes it:

csharp
// Counts the candidates the mutator produces in each iteration the algorithm yields.
public sealed class MutationsPerIterationAnalyzer<TCandidate, TSearchState>(
    IOperator<Mutation, TCandidate> mutator,
    IAlgorithm<TCandidate, TSearchState> algorithm)
    : Analyzer<MutationsPerIteration>,
        IObservationReceiver<MutationObservation<TCandidate>>,
        IObservationReceiver<AlgorithmObservation<TCandidate, TSearchState>>
    where TSearchState : class, ISearchState
{
    // One observation wrapper per boundary, both recording into this analyzer.
    protected override IReadOnlyList<ISubstitution> CreateSubstitutions()
    {
        return [mutator.Invocations.RecordingInto(this), algorithm.Iterations.RecordingInto(this)];
    }

    // Every run creates an empty result of its own.
    public override MutationsPerIteration CreateExecutionNode(ResolutionScope scope) => new();

    // Both recorders look up the same result of the run.
    Action<MutationObservation<TCandidate>>
        IObservationReceiver<MutationObservation<TCandidate>>.CreateRecorder(RunResults results)
    {
        var result = results.Result(this);
        return observation => result.AddMutations(observation.Offspring.Count);
    }

    Action<AlgorithmObservation<TCandidate, TSearchState>>
        IObservationReceiver<AlgorithmObservation<TCandidate, TSearchState>>.CreateRecorder(RunResults results)
    {
        var result = results.Result(this);
        return _ => result.CloseIteration();
    }
}

// The run result synchronizes its own updates, because the boundaries may report concurrently.
public sealed class MutationsPerIteration : IRunResult
{
    private readonly Lock sync = new();
    private readonly List<int> perIteration = [];
    private int pending;

    public void AddMutations(int count)
    {
        lock (sync)
            pending += count;
    }

    public void CloseIteration()
    {
        lock (sync)
        {
            perIteration.Add(pending);
            pending = 0;
        }
    }

    public int[] Snapshot()
    {
        lock (sync)
            return [.. perIteration];
    }
}

Attach it like any other analyzer and read its result after the run:

csharp
var mutationsPerIteration =
    new MutationsPerIterationAnalyzer<RealVector, PopulationState<RealVector>>(
        algorithm.Mutator, algorithm);
var run = algorithm.CreateRun(problem, random, [mutationsPerIteration]);
await run.CompleteAsync(cancellationToken: cancellationToken);

var counts = run.Result(mutationsPerIteration).Snapshot();

The first iteration is the initial population, which the mutator has not touched, so its count is zero. run.Result looks a result up by the analyzer reference, so the analyzer is a class and keeps no collected data itself. The data lives in the result, which keeps independent runs, including concurrent ones, apart. Analyzer architecture describes the library's own analyzers of this kind, such as the Experimental genealogy analyzer.

A clock of your own ​

A custom clock implements IClock<TTime>. Its typed CreateExecutionNode(ResolutionScope) creates a reading for the run. The boxed construction delegates to it. The root owns one reading per clock instance and run. Its Read() may be called concurrently and must preserve the observed computation.

Typed reads such as At(clock) and By(clock) infer TTime through IClock<TTime>. Mixed clock lists use IReadOnlyList<IClock>, and results.Result(clock) infers its type through IClock. Through IClock<TTime> it needs an explicit result type because the typed interface has two configuration-node constructions.

A clock only reads. If it also needs wrappers to update its value, it implements ISubstitution, and the caller lists it after the analyzers that read it. A clock that observes calls holds a private Counter: its recorder increments the run's accumulator, and its reading reads that same root accumulator. It places an Observed wrapper for itself through a SubstitutionGroup. Traces and best-so-far analyzers place no clocks. Clock.Elapsed needs no placement.
