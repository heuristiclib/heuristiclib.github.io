Writing operators ​

Write an operator when your representation or problem needs a search step the built-in operators lack. Configure or compose existing operators first.

An operator configuration is a reusable description. Its executor does the work and owns the mutable fields.

Choose the operator role ​

Pick the role an algorithm already expects.

RoleImplement it when you need to
CreatorProduce initial candidates
EvaluatorCalculate objective vectors outside the problem
SelectorChoose candidates from a population
CrossoverCombine parent candidates
MutatorChange one candidate
RefinerImprove a candidate after variation
ReplacerDecide which candidates survive
InterceptorTransform a produced search state
TerminatorDecide when an algorithm stops

When no role fits, define a new operation.

Choose an authoring path ​

PathTypical baseUse when
StatelessStatelessEvaluator<...>The operation needs configuration values but no mutable execution data
Explicit executorEvaluator<...>The operator resolves child operators or needs complete control over its execution structure

Every role has both paths. The stateless bases derive from the unprefixed role base. An explicit executor derives from the unprefixed base directly.

Some roles add a single-candidate base for operations that treat each item of a batch independently: SingleCandidateMutator<...>, SingleCandidateCrossover<...>, SingleCandidateCreator<...>, SingleCandidateRefiner<...> and SingleCandidateEvaluator<...>. Implement the method for one item, such as MutateCandidate or CrossParents. The inherited batch operation handles batching and forks a random number generator per item. Set Concurrency to run the items concurrently. Each generator is forked from the item's batch position, so the result does not depend on the setting.

Implement a stateless operator ​

This mutator swaps two adjacent elements, so its result stays a permutation:

csharp
using HEAL.HeuristicLib.Encodings.Permutations;
using HEAL.HeuristicLib.Operators.Mutators;
using HEAL.HeuristicLib.Random;

public sealed record AdjacentSwapMutator : SingleCandidateMutator<Permutation>
{
    public override Permutation MutateCandidate(
        Permutation parent,
        IRandomNumberGenerator random)
    {
        if (parent.Count < 2)
            return parent;

        var index = random.NextInt(parent.Count - 1);
        return parent.Swap(index, index + 1);
    }
}

A stateless operation receives what it reads as arguments. That is the search space and problem at the arities that name them, and the objective for selection and replacement. Its configuration values must not change during execution. This evaluator reads its search space and problem:

csharp
private sealed record FirstValueEvaluator
    : StatelessEvaluator<RealVector, BoundedRealVectorSearchSpace, TestFunctionProblem>
{
    public override IReadOnlyList<ObjectiveVector> Evaluate(
        IReadOnlyList<RealVector> candidates,
        IRandomNumberGenerator random,
        BoundedRealVectorSearchSpace searchSpace,
        TestFunctionProblem problem)
    {
        return candidates.Select(candidate => new ObjectiveVector(candidate[0])).ToArray();
    }
}

Choose an arity ​

Each role base comes in three arities. Name only the types the operation reads:

Declared asOperation receivesUse when
SingleCandidateMutator<TCandidate, TSearchSpace, TProblem>parent, random, search space, problemThe operation depends on the problem
SingleCandidateMutator<TCandidate, TSearchSpace>parent, random, search spaceThe operation depends on the search space only
SingleCandidateMutator<TCandidate>parent, randomThe operation depends on the candidate only

The arity changes what the author declares, not where the operator fits. A slot names only the operation and the candidate. AdjacentSwapMutator fills any IOperator<Mutation, Permutation> slot, and so does a mutator written for one specific problem. A run with other types refuses that one before it starts, see Operator type compatibility.

Interceptor and Terminator keep TSearchState at every arity, because they transform or inspect a search state. Terminator<TCandidate> serves conditions that read no input at all, such as elapsed time or cancellation.

Keep private execution data in an executor ​

Never store counters, caches or other run data in configuration properties. Put them in an executor.

An operator with an explicit executor overrides CreateExecutor. The hook receives a typed scope with the bound Problem and SearchSpace, resolves the declared children and returns a private nested Executor. The executor derives from the role's executor base, such as EvaluationExecutor<TCandidate>. Pass it what it reads through its constructor and keep mutable data in its fields:

csharp
public sealed partial record ForwardingEvaluator(IOperator<Evaluation, RealVector> Inner)
    : Evaluator<RealVector, BoundedRealVectorSearchSpace, TestFunctionProblem>
{
    protected override IEvaluationExecutor<RealVector> CreateExecutor<TSearchState>(ResolutionScope<RealVector, BoundedRealVectorSearchSpace, TestFunctionProblem, TSearchState> scope)
    {
        var inner = scope.Resolve(Inner);
        return new Executor(inner);
    }

    private sealed class Executor(IEvaluationExecutor<RealVector> inner)
        : EvaluationExecutor<RealVector>
    {
        public override IReadOnlyList<ObjectiveVector> Evaluate(
            IReadOnlyList<RealVector> candidates,
            IRandomNumberGenerator random)
        {
            return inner.Evaluate(candidates, random);
        }
    }
}

The child is declared as a parameter, so validation and substitution reach it. Each construction starts with fresh fields. Resolving the same configuration and problem again in one scope reuses the executor. To share fields such as a cache, users share the configuration with Sharing, see Sharing executors. Make data that is shared on its own a separate node. Executors are never disposed, so the caller owns any dependency that needs cleanup.

Your operator is observed through Invocations, such as mutator.Invocations, like a built-in one. See Analysis of algorithm runs.

Adaptable parameters ​

To read a value that changes during the run, resolve an IConfigurationNode<IAdaptation> child in CreateExecutor and apply it to the configured base value. GaussianMutator does this for MutationStrength. Adaptable parameters shows the wiring.

Resolve an operator under another objective ​

A selector or a replacer ranks candidates by the objective of the problem it is bound to, and a run binds every operator to the run's problem. An algorithm that needs an operator to rank by another objective than its problem's does not pass the objective to the operator. It resolves the operator under a problem that has that objective.

The example algorithm creates a sample of candidates and keeps the sample's best candidate under a maximizing objective with the BestSelector it holds, which it resolves under a problem that maximizes. In the example's run, whose problem minimizes, that is the sample's worst candidate. The algorithm is written for real vectors in a BoundedRealVectorSearchSpace, because the signature it declares for its selector names the search space. Use these imports in a C# project with implicit system usings enabled:

The delegating problem forwards the evaluation and the search space of the problem of the run and states the objective it was given. It forwards nothing else, so it does not preserve capability interfaces of the run's problem, such as a known optimum, and an operator that reads one of them cannot be resolved under it:

csharp
public sealed class ProblemWithObjective<TCandidate, TSearchSpace>(
    IProblem<TCandidate, TSearchSpace> problem,
    ObjectiveDirections objective)
    : IProblem<TCandidate, TSearchSpace>
    where TSearchSpace : class, ISearchSpace<TCandidate>
{
    public TSearchSpace SearchSpace => problem.SearchSpace;

    public ObjectiveDirections Objective => objective;

    public IReadOnlyList<ObjectiveVector> Evaluate(
        IReadOnlyList<TCandidate> candidates,
        IRandomNumberGenerator random)
    {
        return problem.Evaluate(candidates, random);
    }
}

The algorithm's CreateExecutor creates that problem once and resolves the selector through a typed view of its scope. The selector parameter declares, with ChildExecution, that its child runs under the delegating problem instead of the problem of the run. Preflight validation reads that declaration, so it checks the selector against the problem it is resolved under. Without it, preflight asks the selector about the algorithm's own signature, and a selector written for the delegating problem, one that reads something only that problem has, is rejected before the run starts. A selector such as BestSelector, which accepts any problem, would hide the mismatch. State the same types the hook resolves the child under. The rest of WorstOfSampleAlgorithm is an ordinary iterative algorithm.

csharp
public static Parameter<WorstOfSampleAlgorithm, IOperator<Selection, RealVector>> SelectorParameter { get; } =
    new(nameof(Selector), static algorithm => algorithm.Selector, static (algorithm, value) => algorithm with { Selector = value })
    {
        // The selector is resolved under the delegating problem below, so preflight must ask it about that problem.
        ChildExecution = static _ => ExecutionSignature.For<
            BoundedRealVectorSearchSpace,
            ProblemWithObjective<RealVector, BoundedRealVectorSearchSpace>,
            SingleSolutionState<RealVector>>()
    };

protected override IterativeAlgorithmExecutor<SingleSolutionState<RealVector>> CreateExecutor(
    ResolutionScope<RealVector, BoundedRealVectorSearchSpace, IProblem<RealVector, BoundedRealVectorSearchSpace>, SingleSolutionState<RealVector>> scope)
{
    var interceptor = scope.ResolveOptional(Interceptor);
    var creator = scope.Resolve(Creator);
    var evaluator = scope.Resolve(Evaluator);

    // One problem object per CreateExecutor: it is the objective of everything resolved under it.
    var maximizing = new ProblemWithObjective<RealVector, BoundedRealVectorSearchSpace>(scope.Problem, SingleObjective.Maximize);
    var selector = scope
        .For<RealVector, BoundedRealVectorSearchSpace, ProblemWithObjective<RealVector, BoundedRealVectorSearchSpace>, SingleSolutionState<RealVector>>(maximizing)
        .Resolve(Selector);

    return new Executor(interceptor, creator, evaluator, selector, SampleSize);
}

Four rules apply:

  • One problem object is the single source of the objective for everything resolved under it: the operator, its child operators, refiners and observation records all read the objective of that problem.
  • Create the problem once per CreateExecutor, not per call. A scope keeps one executor for each configuration and problem object, so every new problem object gets new executors that the scope retains. See Sharing executors.
  • The view is the same scope, not a child scope. Executors resolved through it sit beside the executors of the run's problem, and sharing and run results behave as before.
  • Declare the signature of the child on its parameter. The resolution is typed by the delegating problem, so the parameter's ChildExecution names the same types.

This binds an operator to one fixed objective. An objective that changes during a run is not an argument of an operator: see an objective that changes during a run.

Test the contract ​

Test the operator directly before placing it in an algorithm. Check these properties where they apply:

  1. The result belongs to the search space.
  2. The same input and random seed produce the same result.
  3. The input candidate remains unchanged.
  4. Concurrent calls safely coordinate access to shared mutable execution data.

An operator that keeps or requires invariants declares them. Test that the declaration holds.
