Analysis of algorithm runs ​

An analyzer collects typed data from a run, such as a quality curve, a count of evaluations or the offspring of an operator. HeuristicLib provides observability through sources that report events such as completed operator calls and yielded search states. Attach an analyzer to turn those observations into results you can read from the run.

Choose the right tool ​

An analyzer is one of several ways to see what a run does. Ask these questions in order:

Inspection preserves the observed computation while recording its own observations, counts, durations and clocks. Analyzers derive results from those observations. Observation callbacks must preserve the operation's inputs and outputs. Wrappers of your own may change behavior, and explicit algorithm policies such as budgets may read inspection data to decide when to stop. Wrappers forward no controls: a mutator reads its adaptation as a declared node, whichever inspection wrappers surround it.

Best-so-far analysis ​

Analysis involves three parts:

  • An observation source is a boundary that reports what happened, such as algorithm.Evaluator.Invocations for each evaluated batch or algorithm.Iterations for each yielded state.
  • An analyzer is a configuration that describes what to collect from one or more sources. It holds no data, so one analyzer serves any number of runs.
  • A run result holds the collected data. CreateRun attaches the analyzer to one run, and run.Result(analyzer) returns that run's result.

Use a real-vector genetic algorithm, its problem, and a random source from your existing setup. In this example, Analyzer.BestSoFar<RealVector>() observes the algorithm's evaluator and records each improvement of the best objective. run.Result(best) enumerates the recorded points:

Choose what to measure ​

  • Convergence. Read the best objective reached at several evaluation budgets. Quality curves
  • Operator behavior. Count and time mutation calls, and record how many offspring each call returns. Count, time and observe an operator
  • Differences across trials. Compare the median and spread of objective values over repeat runs at a common evaluation budget. Add analysis to an experiment

See Read run-bound results for when results are available. Use Substitute to keep an instrumented configuration for later runs.

Observation sources and clocks ​

Each operator offers its successful invocations as Invocations, and each algorithm offers its yielded states as Iterations. These observation sources describe a boundary. Creating one installs nothing. An evaluator's Invocations observes one completed evaluator invocation, including the whole batch. An algorithm's Iterations observes a yielded state, after its interceptors have transformed that state, and needs no placeholder interceptor. A nested algorithm is a separate observation boundary.

Observation sources match configurations by reference, as Configurations describes. A configuration that never participates produces no observations. Create analyzers for the actual configured objects that will execute. An operator implementing several operations offers each operation's source through that operation's typed view.

A clock gives each recorded entry its time. A Counter counts what its placement observes and a Duration accumulates the time its placement measures. counter.Clock and duration.Clock read them as trace axes. Count, time and observe an operator covers counters and durations. Ready-made traces name their boundary: Analyzer.BestSoFar(algorithm.Evaluator, ...) observes the evaluator, and algorithm.Iterations.TracePopulationQuality(...) observes yielded states. The example records both against one evaluation counter:

csharp
var evaluations = new Counter();
var best = Analyzer.BestSoFar(algorithm.Evaluator, clocks: [evaluations.Clock]);
var population = algorithm.Iterations.TracePopulationQuality(clocks: [evaluations.Clock]);
var run = algorithm.CreateRun(problem, random,
[
    best,
    population,
    algorithm.Evaluator.Invocations.CountingCandidates(evaluations)
]);
await run.CompleteAsync(cancellationToken: cancellationToken);

Counters and durations place nothing: the caller supplies their placement in the substitutions list of CreateRun or in Substitute, as the example does with CountingCandidates(evaluations). A later entry in one list sits closer to its target (Configurations). List a counter's or duration's placement after every analyzer that reads it so the reading includes the call. Listed before them, it reads before the call. A counter or duration placed nowhere reads zero, including when a trace reads it. Several traces may share one clock: place its counting or timing wrapper once, after all those analyzers, to update it once per call before their readings. Separate trace placements add no clock wrappers, so they do not duplicate the count.

algorithm.Iterations.Counting(counter) counts yielded states, algorithm.Calls.Counting(counter) counts started calls, and source.Invocations.Counting(counter) or CountingCandidates(counter) counts successful operator calls or their candidate work. Clock.Elapsed reads the time a run spends advancing its algorithm, including a call in progress. Executor construction before the first advance, pauses and consumer work are excluded. Deferred child construction during an advance, such as a fresh Cycle turn, is included. Direct scope execution leaves it and scope.Results.Elapsed at zero. Use algorithm.Timed(duration) for explicit measurement there. Sharing executors explains how counters and durations accumulate across a cycle's turns.

Equal clocks identify one column of every entry, including when a clock is supplied twice. Repeated counter.Clock reads give equal clocks, and new ElapsedClock() reads the column selected with Clock.Elapsed. Clocks of two distinct counters identify two columns. A class clock without an equality override, such as the epoch clock, matches by reference. Keep that instance to project its column. TraceEntry.At(clock) and BestSoFarPoint.At(clock) read the column of the equal clock the analyzer was given, and By(clock) on a trace result or snapshot projects it for every entry. A clock the analyzer was not given throws InvalidOperationException.

Read a trace through run.Result(trace). Its SampleCount and Latest properties do not allocate. Latest is null before an entry is recorded. Snapshot() and By(clock) allocate stable copies without stopping collection, so a trace can also be read during execution. Take one snapshot when you want consistent projections onto several axes. The example projects it onto a single axis, the evaluation counter. A trace created with clocks: [evaluations.Clock, Clock.Elapsed] would also offer snapshot.By(Clock.Elapsed), a second axis over the same entries:

csharp
var snapshot = run.Result(population).Snapshot();
var byEvaluations = snapshot.By(evaluations.Clock);
1
2

A snapshot preserves its selected axes even when empty. Selected clocks are read when an entry is recorded. Clocks on independent concurrent boundaries do not promise an atomic global timestamp.

Candidate counts describe the selected boundary. A caching evaluator's outer boundary counts requests while its inner evaluator counts cache misses. An operation without candidate work rejects Invocations.CountingCandidates(counter) when the substitution is created. Use Invocations.Counting(counter) for its calls.

Traces and retention ​

TracePopulationQuality records the current best, median, and worst of each observation's objective vectors, such as those of a yielded population. Use TracePopulationCandidates for population candidates.

csharp
var iterations = new Counter();
var evaluations = new Counter();
var quality = algorithm.Iterations.TracePopulationQuality(
    clocks: [iterations.Clock],
    retention: TraceRetention.EveryNth(10));
var bestAtEveryEvaluation = Analyzer.BestSoFar(algorithm.Evaluator,
    clocks: [evaluations.Clock],
    retention: TraceRetention.EveryObservation());
var run = algorithm.CreateRun(Problem, RandomNumberGenerator.Create(seed: 42),
[
    quality,
    bestAtEveryEvaluation,
    algorithm.Iterations.Counting(iterations),
    algorithm.Evaluator.Invocations.CountingCandidates(evaluations)
]);

TraceRetention.EveryObservation() keeps each observation, so a best-so-far analyzer records one point for every non-empty evaluation batch and not only its improvements. A batch that evaluates nothing records no point. TraceRetention.EveryNth(10) records observations 10, 20, 30, and so on, with no extra initial or final entry. OnChange() records the first value and subsequent changes by equality. LatestOnly() replaces the preceding entry. Retention policies are immutable, and each result creates its own retention progress even when several traces or runs use one policy.

Retention runs after a trace's function reads an observation. It controls stored entries and never skips expensive computations, so best-so-far still sees an improvement between retained observations. EveryNth and OnChange leave stored entries alone. LatestOnly is the one policy that discards what the trace already held.

Custom traces ​

Analyzer.Trace reads one value from each observation of a source through a function:

csharp
var size = algorithm.Iterations.Trace(
    observation => observation.State.Population.EvaluatedCandidates.Count);
var offspring = crossover.Invocations.Trace(observation => observation.Offspring.Count);
var quality = evaluator.Invocations.Trace(
    observation => observation.ObjectiveVectors.BestMedianWorst(observation.Problem.Objective));
1
2
3
4
5

Each operation has its own observation record, such as CrossoverObservation<TCandidate> with Parents and Offspring, or EvaluationObservation<TCandidate> with Candidates and ObjectiveVectors. It holds the invocation's inputs and outputs and reads the search space and problem at the candidate's interfaces, so it fits every run over the candidate. Each batch is an immutable ValueArray<T> snapshot, reusing existing immutable storage where possible, so an observer never sees a later change to a list an operator reuses. The candidates in a batch are live references, not isolated deep copies.

Counting, collecting and single values are plain functions of the observation. Ranking functions such as Best and BestMedianWorst receive the objective directions they order by, usually the observed invocation's own, observation.Problem.Objective, so each invocation is ranked by its own problem. MinMeanMax summarizes plain numbers and needs no directions.

Accumulating analyzers ​

Some analysis produces one mutable summary rather than a history. Use source.Aggregate(create, update) to create plain state for each run and update it from observations. Read the state with run.Result(summary).Value. Updates are serialized per run. Reading the state during execution is the state type's concern:

csharp
var summary = algorithm.Evaluator.Invocations.Aggregate(
    () => new CandidateSummary<RealVector>(),
    (state, observation) => state.Add(observation.Candidates));

public sealed class CandidateSummary<TCandidate>
{
    private readonly List<TCandidate> candidates = [];

    // Read the live collection once execution has stopped.
    public IReadOnlyList<TCandidate> Candidates => candidates;

    public void Add(IReadOnlyList<TCandidate> batch)
    {
        candidates.AddRange(batch);

Read an accumulating analyzer after the run finishes, as for accumulating results such as a Pareto front or a genealogy graph. Its result spans the whole run, including Cycle turns. Sharing does not narrow the result that recording and run.Result use. Share counters and durations, not analyzers: resolving a shared analyzer directly gives a separate result that nothing records into. Aggregate and Trace read one observation type. To combine different types, such as mutator invocations and algorithm iterations, write an analyzer over several observation types. Clocks and retention apply to trace entries, so they do not apply to a single mutable summary.

Evaluator selection for best-so-far analysis ​

Analyzer.BestSoFar keeps the best candidate across evaluator observations and records only improvements by default. Each point retains its candidate directly and gives Evaluations, Value and Candidate.

Without a named evaluator, Analyzer.BestSoFar<TCandidate>() observes evaluators of that candidate type holding no such evaluator among their declared descendants. A cache therefore counts misses at its inner evaluator. Evaluators inside refiners count too. For composite evaluations or refinement against another problem, name the intended evaluator with Analyzer.BestSoFar(evaluator). Explicit placement counts inside the observer with evaluator.Counted(best.Evaluations, OperatorCountMetric.Candidates).Observed(best). Time is optional: pass clocks: [Clock.Elapsed] and read point.At(Clock.Elapsed).

Keep a best-so-far of your own ​

A best-so-far object keeps the running best across observations inside a custom trace. BestSoFar keeps an objective vector, and BestSoFar<T> keeps a value ranked by its selected objective vector. Supply a state factory so every run creates a separate accumulator:

csharp
var bestSoFar = evaluator.Invocations.Trace(() => new BestSoFar(),
    (best, observation) => best.Update(observation.ObjectiveVectors, observation.Problem.Objective));
1
2

The first directions a best-so-far accumulator receives fix its ordering. Other directions or dimensionality throw. Ready-made traces create their accumulation state per run. State deliberately captured by a caller's own delegate remains the caller's responsibility.

Combine several sources in one trace ​

To collect several sources of one observation type into one accumulator and result sink, create one combined trace:

csharp
var sources = new[]
{
    firstAlgorithm.Evaluator.Invocations,
    secondAlgorithm.Evaluator.Invocations
};
var combined = Analyzer.Trace(sources, () => new BestSoFar(),
    (best, observation) => best.Update(observation.ObjectiveVectors, observation.Problem.Objective),
    retention: TraceRetention.OnChange());

Count, time and observe an operator ​

CreateRun or Substitute applies counting and timing substitutions alongside observation callbacks:

csharp
var counting = new Counter();
var timing = new Duration();
var observation = algorithm.Mutator.Invocations.Observing(
    value => offspring.Add(value.Offspring.Count));
var run = algorithm.CreateRun(problem, random,
[
    observation,
    algorithm.Mutator.Invocations.Counting(counting),
    algorithm.Mutator.Invocations.Timing(timing)
]);
await run.CompleteAsync(cancellationToken: cancellationToken);

Pass everything in one CreateRun substitutions list or one Substitute call. Configurations explains how the substitutions of one call combine. All three name the same mutator, and a later entry sits closer to it, so the run calls Observe(Count(Time(mutator))). The timing wrapper finishes first, then the count updates, and the observation callback runs last. Listing the timing substitution, algorithm.Mutator.Invocations.Timing(timing), before observation instead would put the observation inside the timed region, so the measured duration would include the callback. Counting updates after success. Timing also records failed calls.

Create counters with new Counter() and durations with new Duration(). Invocations.Counting(counter), CountingCandidates(counter) and Timing(duration) return substitutions placing their wrappers. algorithm.Iterations.Timing(duration) times an algorithm's calls the same way. Read their accumulators through the run, as Configurations shows. Counted and Timed place the same wrappers directly around a selected configuration. The wrapper decides what is counted, so pass OperatorCountMetric.Candidates to Counted to count candidate work.

Share accounting with a terminator ​

A count terminator holds the counter whose result it reads. Place a counting wrapper for that counter so successful calls update the same run-bound result:

csharp
var mutations = new Counter();
var limited = algorithm.TerminatedBy(
    new AfterOperatorCountTerminator<RealVector>(mutations, 2));
var run = limited.CreateRun(problem, random,
    [algorithm.Mutator.Invocations.Counting(mutations)]);

await run.CompleteAsync(cancellationToken: cancellationToken);
var measuredCount = run.Result(mutations).CurrentCount;

Select configurations by properties or names ​

Substitute places a wrapper wherever a selection matches, as Configurations describes. Select by the type of the lambda's parameter to wrap every configuration of a role:

csharp

Select by name ​

Name a configured operator through .Named(name) and select that boundary explicitly:

csharp
var exploration = mutator.Named("exploration");
Func<IOperator<Mutation, RealVector>, bool> selected =
    node => node is INamedConfiguration { Name: "exploration" };
Func<IOperator<Mutation, RealVector>, bool> otherExploration =
    node => selected(node) && !ReferenceEquals(node, exploration);
1
2
3
4
5

The receiver here is an IOperator<Mutation, RealVector>, which fixes the operation the wrapper names. One Named<TOperation, TCandidate> serves every operator role: creators, crossovers, evaluators, mutators, refiners, replacers, selectors, interceptors and terminators. Create it with .Named(name) or Named.Create(child, name). Algorithms use NamedAlgorithm.Create(child, name) or algorithm.Named(name). A consumer-defined configuration can implement INamedConfiguration directly.

Names compare exactly and case-sensitively. Several nodes may share a name, and all match. The wrapper and its child are separate configuration nodes: a name selects the wrapper, while a selection by role type can select both boundaries. Names do not change execution sharing or create caller paths. The child's concrete properties remain on the child configuration.

A name is useful when you cannot hold a reference to the target. Configurations built separately, for example by a factory method, contain equal but distinct nodes, so a reference selection matches only one of them. A name you assigned when building each configuration selects the same logical boundary in all of them.

Cycles and turns ​

An algorithm observation's Iteration numbers the iterations of one call, as the algorithm sees them. A meta-algorithm that runs an inner algorithm again calls it again, so the inner iterations number from 1 again, whether its executor is fresh or reused. A clock over the iterations keeps counting across those calls.

A turn is one call of an inner algorithm. Its Calls source reports Started, then Completed, Failed or Stopped, including calls that yield no states. There is no separate cycle-start observation source: observe a cycle through the turns of its inner algorithms. The example counts calls of exploitation and combines both inner algorithms' call events:

csharp
var cycle = CycleAlgorithm.Create(exploration, exploitation) with { MaximumCycles = 2 };
var calls = new Counter();
var iteration = exploitation.Iterations.Trace(observation => observation.Iteration, [calls.Clock]);
var turns = Analyzer.Trace(new[] { exploration.Calls, exploitation.Calls }, call => call.Event);
var run = cycle.CreateRun(problem, random,
    [iteration, turns, exploitation.Calls.Counting(calls)]);
await run.CompleteAsync(cancellationToken: cancellationToken);

exploitation runs two iterations per call. Its iteration trace holds (1, 1), (1, 2), (2, 1) and (2, 2) against its call counter. A Started observation reads that counter before its own call is counted. Yielded states and the call's end read the updated count. The combined event trace records both inner algorithms. Call observations provide no cycle number or slot index.

Multi-objective ranking ​

Single-objective traces use the observed problem's objective comparer automatically. A multi-objective problem without a total order cannot supply a unique best, median, or worst. Ranking throws when first required, even for a singleton batch. There is no implicit lexicographic fallback.

Select an objective comparer explicitly when the trace needs a total order:

csharp
var best = Analyzer.BestSoFar(algorithm.Evaluator,
    objectiveComparer: new LexicographicComparer(problem.Objective.Directions));
1
2

This makes dimension priority explicit and affects this trace's comparisons, including best-so-far accumulation. It does not change the problem or algorithm's objective. Analysis accepts the objective system's existing IComparer<ObjectiveVector> implementations. The RequireTotalOrder helper also serves callers outside analysis. A missing total order is reported when an observation is ranked, because the problem is known only then.

To follow progress by dominance instead of imposing an order, measure the accumulated front. Track progress toward the front traces its hypervolume with the Experimental package.

Experiments ​

An experiment runs the parameter candidates of its grids on each problem and repetition. Pass the same analyzers in the list of its CreateRun and read each trial's result through trial.Run.Result(analyzer). Experiments shows how placement works when parameter candidates vary.

Observations and clocks of your own ​

An analyzer that combines several observation types, or a clock that reads something other than iterations, evaluations or elapsed time, is written against the same contracts the built-in ones use. Observations and clocks shows both.

Sources and IObservable<T> ​

A source resembles a cold IObservable<T>: it describes observations without producing any until something subscribes. Here, a trace from Analyzer.Trace or a callback from Observing subscribes when Substitute places it in the configuration. The library implements neither IObservable<T> nor Rx-style operators. A callback can feed observations into Rx, for example into a subject:

csharp
var subject = new Subject<CrossoverObservation<RealVector>>();
var feed = crossover.Invocations.Observing(subject.OnNext);
var run = algorithm.CreateRun(problem, random, [feed]);
1
2
3

The callback runs on the thread that invoked the operator, inside the wrapped invocation. Configurations covers what a callback means for persisting the configuration and who owns the state it captures.
